不必先把整个博客系统研究明白。先写一个具体问题，再把它整理成文章。

## 新建一篇文章

在项目目录运行：

```sh
npm run new -- my-first-post "我的第一篇文章"
```

脚本会生成 `src/content/blog/my-first-post/index.md`。文件夹名决定网址，所以建议使用小写英文和连字符。

文件最上方的部分叫 frontmatter，用来描述文章信息：

```yaml
---
title: "我的第一篇文章"
description: "用一两句话说明这篇文章讲什么。"
date: 2026-11-11
tags: [写作与整理]
draft: true
---
```

正文写在第二条分隔线下方。网页会自动显示标题，正文从二级标题开始即可。

## 先把一个问题讲清楚

技术记录可以使用下面的结构：

1. 遇到了什么现象。
2. 当时是什么环境。
3. 用什么证据判断原因。
4. 做了哪些操作。
5. 怎样确认问题已经解决。

没有验证的猜测，就写成猜测。命令的实际输出与预期结果也要分开。

## 常用排版

### 标题与段落

用 `##` 创建章节，`###` 创建小节。段落之间空一行，不需要在每行末尾添加特殊符号。

**重点可以加粗**，但不必给整段话加粗。能让读者迅速找到重点，才是格式的作用。

### 代码与命令

代码块注明语言，阅读时更容易识别：

```sh
pwd
ls -la
```

把真实输出单独放在代码块里，避免读者把结果也当成命令复制。

### 图片与说明

把图片放到文章文件夹，用相对路径插入：

```markdown
![说明这张图展示了什么](./network.png)
```

文件名尽量简单，不使用临时下载链接。图片说明应帮助理解，而不是写成「图片 1」。

## 从草稿到发布

`draft: true` 的文章不会出现在页面、搜索、RSS 或站点地图里。本地查看草稿时，可暂时改为 `false`，然后启动预览：

```sh
npm run dev
```

准备发布时，保留 `draft: false`，再执行：

```sh
npm run build
npm run check:site
```

检查通过以后，再提交到自己的 GitHub 仓库。

注意：草稿开关只影响博客生成结果。如果 GitHub 仓库是公开的，源文件仍然可以被看到。

## 好文章来自真实记录

不必为了让文章完整而补出一次并没有发生的实验。保留适用条件、实际现象和验证结果，这样以后遇到相似问题，文章才真正有用。
